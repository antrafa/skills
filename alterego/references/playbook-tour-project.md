# Playbook: Technical Project Tour (`/alterego tour-project`)

This playbook guides the complete technical onboarding of a developer into a
new repository or codebase. It turns the cold analysis of files into a
**pedagogical, architectural and practical guided tour**, as if a senior tech
lead were sitting next to you explaining the system from scratch.

---

## Invocation modes

```
/alterego tour-project                   (full tour of the codebase)
/alterego tour-project <focus>           (focused tour: e.g. auth, payments, queue)
```

In Codex:
```
$alterego tour-project
```

---

## 1. Reconnaissance step (before explaining)

Before generating the explanation:
1. **Identify the stack:** read manifest files (`package.json`, `pom.xml`, `go.mod`, `Cargo.toml`, `requirements.txt`, `composer.json`, etc.).
2. **Understand the architectural style:** monolith, microservices, serverless, modular, BFF, desktop/Tauri, lib/CLI.
3. **Quick alignment:**
   - If the user did not specify a focus in the invocation, ask once: *"Is there a specific area you want to focus on (e.g. authentication, payment flow, integration X), or do you prefer the full overview?"*
   - Ask about or confirm the save location:
     - **Default fallback:** `docs/tour-project/tour-[project-name].md`
     - If the user gives another path, respect their choice.

---

## 2. Structure of the technical tour

**Zoom level is the backbone of the tour** (C4 model, Simon Brown). A tour that
mixes "this system charges the customer" with "this method caches the token"
loses the reader on the first turn. Each block sits at one level and says which:

| Level | It answers | Where it shows up in the tour |
|---|---|---|
| **1. Context** | who uses the system and which others it talks to | blocks 1 and 2 |
| **2. Container** | which deployable pieces exist (API, worker, SPA, database) and how they communicate | blocks 2, 5 and 8 |
| **3. Component** | inside one container, which parts carry the responsibilities | blocks 3, 4 and 7 |
| **4. Code** | the classes and functions that matter | block 6 |

Never open at level 4, however interesting the code is: someone who does not
know what the system is for cannot tell an important class from an incidental
one. Each diagram declares its level in the title (*"Level 2 — Containers"*),
and the study order in block 10 follows the same descent.

Every tour generated by Alterego follows these 10 blocks:

### 1. Purpose of the system (in plain language)
- What real-world problem does this system solve?
- Who are the users (humans or other systems)?
- What is the main business value flow?

### 2. Overall architecture & stack
- **System type:** Frontend, Backend, Fullstack, Desktop, Worker/Job, etc.
- **Technology stack:** Language, framework, critical libraries and tools.
- **Why these technologies:** the role each choice plays in the architecture.

### 3. Directory structure (the treasure map)
Walk through the main folders (adapting to the project's reality: `src/`, `internal/`, `lib/`, `modules/`, `domain/`, etc.):
- Responsibility of each directory;
- What lives inside it;
- How it connects to the other parts.

### 4. Critical points & core elements
Sweep ordered by importance (from the most central to the peripheral):
- Controllers / Entrypoints / Handlers
- Services / Use Cases / Domain
- Stores / State Management / Hooks
- Providers / Middlewares / Interceptors
- Jobs / Schedulers / Workers / Queues
- Database / Repositories / Migrations
- External APIs and integrations

*Rule:* Always include clickable links in the format `[FileName](file:///path/file.ext#L10)`.

### 5. The main execution flow (visual)
Draw the end-to-end flow (request comes in → processing → state/database → response):
- **Mermaid diagram** (`sequenceDiagram` or `flowchart TD`).
- ASCII fallback in case the user is in a plain terminal with no renderer.

### 6. The most important files, line by line
Select 3 to 5 files that are the "heart" of the application:
- Exact responsibility;
- Input and output contracts;
- Business rules it contains;
- Relevant code snippets, commented through the persona's eyes.

### 7. Where state lives (state management)
- **Frontend:** how global state is born, flows and reacts (Zustand, Redux, Context, Signals).
- **Backend:** where application state resides (session, Redis cache, transactional database, messaging).

### 8. Integrations and external boundaries
- Which external services does it consume (APIs, webhooks, cloud services)?
- Which endpoints does it expose to third parties?
- What happens if an external integration fails?

### 9. Technical debt, traps & risks
The critical eye of a senior tech lead:
- Where is there excessive coupling or overly complex code?
- Which parts have no tests or have fragile tests?
- Concurrency, performance (N+1) or security risks observed.

### 10. Onboarding runbook: "the ideal order to study"
Build a numbered chronological trail for the newcomer dev:
1. `[README.md](file:///...)` — Overview and startup commands;
2. `[config/...](file:///...)` — Environment variables and contracts;
3. `[src/domain/...](file:///...)` — Core models and business rules;
4. `[src/services/...](file:///...)` — Main use cases;
5. `[src/api/...](file:///...)` — Endpoints and validation;
6. `[tests/...](file:///...)` — Real expected scenarios.

---

## 3. Output and saving the artifact

1. Show the tour in the chat or in well-structured topics.
2. Save the full version at:
   - `docs/tour-project/tour-[project-name].md` (as the default fallback)
   - Or at the path explicitly requested by the user.
3. If the `docs/tour-project/` directory does not exist, create it.
4. Finish by stating the path of the saved file and offering to go deeper into any of the parts.
