## Anatomy of a .gitlab-ci.yml

```yaml
stages:
  - build
  - test
  - deploy

build:
  stage: build
  image: docker:24
  services: [docker:24-dind]
  variables:
    DOCKER_TLS_CERTDIR: "/certs"
  script:
    - echo "$CI_REGISTRY_PASSWORD" | docker login -u "$CI_REGISTRY_USER" --password-stdin "$CI_REGISTRY"
    - docker build -t "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA" .
    - docker push "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA"
  rules:
    - if: '$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'

test:
  stage: test
  image: node:20
  script:
    - npm ci --cache .npm --prefer-offline
    - npm test
  cache:
    key:
      files: [package-lock.json]
    paths: [.npm/]

deploy:
  stage: deploy
  image: alpine/k8s:1.35.8   # pinned version, close to the cluster's; never latest
  script:
    - kubectl set image deploy/meu-app app="$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA" -n meu-namespace
    - kubectl rollout status deploy/meu-app -n meu-namespace --timeout=5m
  environment:
    name: producao
  rules:
    - if: '$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'
      when: manual
```

The `test` cache keeps `.npm/`, not `node_modules/`: `npm ci` deletes
`node_modules/` before installing, so caching that folder speeds up nothing.

`stages` defines the order; jobs in the same stage run in parallel. The
pipeline only advances to the next stage when every job of the current one
passes (except a job with `allow_failure: true`).

## rules vs only/except

`only`/`except` no longer gets new development in GitLab; `rules` is the
recommended one and allows compound conditions:

```yaml
rules:
  - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
    when: always
  - if: '$CI_COMMIT_BRANCH == "main"'
    when: on_success
  - when: never   # explicit fallback: do not run in any other case
```

Order matters — `rules` evaluates top to bottom and stops at the first one
that matches. Forget the final `when: never` and the job can run in
situations you did not foresee (e.g. on every tag, every branch).

## cache vs artifacts

They are different concepts, and confusing them is the most common cause of
a slow pipeline or a job that does not find an expected file:

- **`cache`**: speeds up future runs (e.g. `node_modules/`,
  `.m2/repository`). It is not guaranteed between jobs/pipelines — treat it
  as an optimization, never as transport for an artifact the next stage
  needs.
- **`artifacts`**: files generated by a job that **must** be available to the
  following jobs of the same pipeline (e.g. compiled binary, test report,
  image built as a tarball). They are passed explicitly between stages.

```yaml
build:
  script: [make build]
  artifacts:
    paths: [dist/]
    expire_in: 1 day

deploy:
  script: [./deploy.sh dist/]   # depends on the previous job's artifact
```

If a job in the next stage needs a file generated earlier, that is
`artifacts`, never `cache` — the cache may not exist on the runner machine
that picked up the next job.

## Variables and secrets

- Sensitive variables (tokens, passwords, keys) go in the project/group
  **CI/CD Variables** in GitLab (Settings → CI/CD → Variables), marked as
  **Protected** (only available on protected branches/tags) and **Masked**
  (hidden in the log) — never hardcoded in `.gitlab-ci.yml`.
- A variable marked `Protected` is not available on unprotected branches —
  if a job fails because of an "empty" variable only in a feature-branch MR,
  this is the most common cause.
- For the **project's own** registry, use the predefined variables
  `$CI_REGISTRY`, `$CI_REGISTRY_USER`, `$CI_REGISTRY_PASSWORD` (derived from
  `$CI_JOB_TOKEN`) and `$CI_REGISTRY_IMAGE` — there is no need to register any
  variable, and the token expires with the job. Only create a
  protected/masked CI/CD Variable when the target is external to the project
  (third-party registry, cluster, cloud). A registry password hardcoded in
  `.gitlab-ci.yml` is already in the git history: besides removing it,
  advise **rotating** the credential.

## Runners and tags

Jobs only run on runners whose `tags` match the `tags:` declared in the job:

```yaml
deploy:
  tags: [kubernetes, producao]
```

A job stuck in "pending" indefinitely is almost always a tag with no matching
runner available — check in Settings → CI/CD → Runners which tags each runner
accepts before investigating any other cause.

## build → test → deploy pipeline pattern

1. **build**: compiles/packages and publishes the versioned artifact (Docker
   image with an immutable tag, e.g. the commit SHA — never `latest` for a
   traceable deploy).
2. **test**: runs tests against the artifact generated in build, does not
   recompile.
3. **deploy**: applies the already tested artifact to the target
   environment. A production deploy must be `when: manual` unless the team
   has explicitly decided on automatic continuous deployment.

Reusing the same build artifact in every following stage (via `artifacts` or
a fixed image tag) guarantees that what was tested is exactly what goes to
production — rebuilding in each stage opens a gap between what was tested and
what was deployed.

Use `needs:` to declare the real dependency between jobs (`deploy` needs
`package`, not "the whole previous stage") — besides making the graph
explicit, it lets independent jobs run without waiting for the whole stage.

### Building a Docker image inside the pipeline

- The job that runs `docker build` needs an image with the docker binary
  (`docker:24`) and the `docker:24-dind` service — `bitnami/kubectl` and
  language images do not have docker. Mixing `docker build` and `kubectl` in
  the same job is a sign that a `package` stage is missing.
- With dind, declare `DOCKER_TLS_CERTDIR: "/certs"` (the default documented
  by GitLab) — without it, the connection between the job and the daemon
  fails in an intermittent and confusing way. The runner must be in
  privileged mode; if it cannot be, the alternative is kaniko or buildah.
- **`kubectl set image` with the same tag does nothing.** If the image is
  always `:latest`, the field value does not change, the Deployment sees no
  change and does not roll out — the pipeline "passes" and production keeps
  running the old version. Publish with a per-commit tag
  (`$CI_COMMIT_SHORT_SHA`) and close the job with `kubectl rollout status` so
  it fails if the new pod does not come up.

## Failing job: common causes

| Symptom | Likely cause |
|---|---|
| Job stuck in "pending" | No runner with the job's `tag` available/online |
| Variable apparently empty only on a non-main branch | Variable marked `Protected` in the project |
| `node_modules`/dependencies "disappear" between jobs | Used `cache` for something that should be `artifacts` |
| Job passes locally but fails on the runner | Base image different from the one used locally, or a dependency on local environment state not declared in `script` |
| Pipeline fires on every commit, including unexpected tags/MRs | Missing explicit `rules` with a `when: never` fallback |
| Deploy applies the wrong version | Artifact rebuilt in the deploy job instead of reusing the already tested artifact |
| Deploy "passes" but production stays on the old version | `kubectl set image` with a repeated tag (`:latest`) does not change the Deployment; missing per-commit tag + `rollout status` |
| `docker build` fails with "Cannot connect to the Docker daemon" | Job without the dind service, image without the docker binary, or `DOCKER_TLS_CERTDIR` missing |
